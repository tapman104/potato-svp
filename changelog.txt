# Changelog — Potato MPV Engine Split & Smoke Test

## Architecture: splitting BaseMPVView
- Identified that mpv-android's `BaseMPVView.kt` mixed the MPV engine
  (init, destroy, playback commands) directly into a `SurfaceView` subclass,
  making the engine impossible to reuse or test without a live Android View.
- Split `BaseMPVView.kt` into two files:
  - `MpvEngine.kt` — pure engine logic, zero `android.view.*` imports.
    `open class MpvEngine(appContext: Context)`. Exposes `initialize()`,
    `destroy()`, `playFile()`, `setVo()`, and surface lifecycle hooks
    (`onSurfaceCreated(surface: Surface)`, `onSurfaceChanged(w, h)`,
    `onSurfaceDestroyed()`) as plain methods instead of
    `SurfaceHolder.Callback` overrides.
  - `MpvSurfaceView.kt` — thin `SurfaceView` + `SurfaceHolder.Callback` shim
    that forwards each callback to the matching `MpvEngine` method. Added a
    secondary constructor (`MpvSurfaceView(context, engine)`, no
    `AttributeSet` required) for use from Compose's `AndroidView`.
- Verified the split compiled cleanly against `MPVLib.kt` and the AAR using
  `kotlinc` directly, confirmed no behavior was lost via a unified diff
  against the original `BaseMPVView.kt` (idle=once quirk, force-window
  dance, and pending-file-load logic all preserved).
- Confirmed no other code in the workspace referenced `BaseMPVView`, so the
  original file was saved as a reference copy rather than wired into any
  build.

## Project: standing up `potato mpc` as its own Gradle project
- Discovered `potato mpc` (Desktop scratch folder) had no Gradle project —
  only loose `.kt` files. The real, build-tested project was `potato ultra x`,
  which uses the richer, production-grade `MpvWrapper` engine (not
  `MpvEngine`) plus Hilt DI, nav graph, and other app features.
- Decided to keep `potato mpc` on the simpler `MpvEngine`/`MpvSurfaceView`
  split (already working) rather than pulling in `MpvWrapper`'s larger
  dependency surface, to keep the smoke-test project minimal.
- Copied only Gradle scaffolding (not source) from `potato ultra x` into
  `potato mpc`: `settings.gradle.kts`, root `build.gradle.kts`,
  `gradle.properties`, `gradle/libs.versions.toml`, `gradle/wrapper/`,
  `gradlew`/`gradlew.bat`, `local.properties`, `libs/mpv-android-lib-v1.0.0.aar`.
- Trimmed `app/build.gradle.kts` down to Compose BOM, Material3,
  activity-compose, lifecycle-viewmodel-compose, coroutines, and the AAR
  dependency — removed Hilt, Navigation, Room, Coil, Serialization, KSP.
  Set `applicationId = "com.potato.smoketest"` to avoid collision with
  `potato ultra x` on the same device.
- Trimmed `AndroidManifest.xml` to a single activity, removed FileProvider,
  unused permissions, and the production `PotatoApplication` class.
- Verified the empty shell synced via `.\gradlew.bat tasks` (first run 36.5s
  cold, 18s warm) before any source was added.
- Hit an IDE import error ("Can't use Java 25.0.4.1 and Gradle 8.9") — fixed
  by setting the IDE's Gradle JVM to Java 21, keeping Gradle itself on 8.9
  to match `potato ultra x`'s configuration (chose this over upgrading
  Gradle to 9.7.1, to keep both projects on the same Gradle version).
- Moved the six previously-split/saved source files
  (`MPVLib.kt`, `MpvEngine.kt`, `MpvSurfaceView.kt`, `PlayerViewModel.kt`,
  `PlayScreen.kt`, `MainActivity.kt`) into
  `app/src/main/java/is/xyz/mpv/`, matching their existing package
  declaration. Updated the manifest to declare this `MainActivity` as the
  launcher.
- First full build (`assembleDebug`) succeeded — produced per-ABI debug
  APKs (arm64-v8a, armeabi-v7a, x86_64, x86).

## Crash #1: `NoSuchMethodError` on `MPVLib.eventProperty`
- App crashed immediately on launch with:
  `NoSuchMethodError: no static method
  "Lis/xyz/mpv/MPVLib;.eventProperty(Ljava/lang/String;Lis/xyz/mpv/MPVNode;)V"`,
  fatal inside `MPVLib.create()` → `MpvEngine.initialize()`.
- Root-caused via direct binary inspection of `libplayer.so` (extracted from
  the AAR, disassembled with NDK `llvm-objdump`/`llvm-nm`): the native
  library's `init_methods_cache` function resolves 8 JNI callback method IDs
  up front via `GetStaticMethodID`, including
  `eventProperty(String, MPVNode)` and `event(Int, MPVNode)` — neither of
  which existed in the project's `MPVLib.kt`.
- Confirmed via comparison with the exact upstream fork the AAR was built
  from (`abdallahmehiz/mpv-android`, `node` branch / PR #1156) that these
  two `MPVNode`-based overloads are real, expected methods, missing only
  from this project's copy of `MPVLib.kt`.
- Fix: added both missing `@JvmStatic` overloads to `MPVLib.kt`
  (`eventProperty(String, MPVNode)`, `event(Int, MPVNode)`), gave
  `EventObserver`'s interface methods default (empty) bodies so existing
  implementers don't break, added a default `event(Int, MPVNode)` that
  forwards to `event(Int)` for backward compatibility.
- Verified via `javap` on the compiled `.class` output that all 8 expected
  static methods are now present with the correct signatures.
- Rebuilt, reinstalled, relaunched — zero fatal errors, surface attached,
  activity reached `RESUMED` state.

## Bug #2: video not rendering (audio-only playback)
- After fixing the crash and wiring the file picker, picking a video played
  audio but showed no video frame. Logcat showed MPV correctly opening the
  file, selecting the h264 decoder, and reaching
  `playback-restart complete ... audio=playing, video=playing` — but the
  video-output line read `VO: [null] 480x864 yuv420p` instead of `[gpu]`.
- Root cause: on backgrounding the activity (e.g. for the file picker),
  `MpvEngine.onSurfaceDestroyed()` sets `vo` to `"null"` as part of the
  standard teardown. When the activity resumed and the surface reattached,
  the code path that should restore `vo` back to `"gpu"`
  (`MPVLib.setPropertyString("vo", voInUse)`) was not being hit before the
  next `loadfile` command — likely bypassed by an earlier change that made
  `playFile()` send `loadfile` immediately instead of always going through
  the surface-reattach restore logic.
- Fix applied to `MpvEngine.kt`'s surface-reattach path to explicitly
  restore `vo` to `"gpu"` on reattach, before any pending or new file load
  proceeds.
- Rebuilt, reinstalled, relaunched, picked the same test video again —
  confirmed via logcat and device screenshot that video now renders
  (session ended mid-verification; final screenshot confirmation was in
  progress).

# Changelog — Potato Player (PlayScreen tap-handling fix)

## Fixed
- **Controls auto-hide timer not resetting on interaction**
  Previously, the 5-second auto-hide timer for playback controls only reset
  when tapping to reveal controls — not when pressing play/pause, seeking,
  or using the back/open-file actions. The timer now resets explicitly from
  each user action: `onPlayPauseClick`, `onSeek`, `onSeekStarted`,
  `onBackClick`, `onOpenFileClick`.

- **Redundant tap-gesture detectors causing multiple timer resets per tap**
  `PlayerTopBar` and the bottom bar host each had their own
  `detectTapGestures` listener layered on top of per-action resets, causing
  `resetHideTimer()` to fire up to three times for a single control tap.
  Removed the redundant bar-level detectors; each user action now resets
  the timer exactly once, from a single explicit call site.

- **Undocumented tap-leakage prevention between video surface and controls**
  The mechanism preventing a tap on play/pause or the seek bar from also
  toggling controls visibility (via the full-screen background tap
  detector) was implicit and unexplained. Added an inline code comment in
  `PlayScreen.kt` documenting that this relies on `detectTapGestures`'s
  `awaitFirstDown(requireUnconsumed = true)` behavior, which ignores
  pointer-down events already consumed by child controls (`IconButton`,
  `Slider`).

## Verified
- Device-tested via ADB input + logcat on a connected device:
  - Tapping play/pause: timer resets exactly once, controls stay visible.
  - Tapping/dragging the seek bar: controls stay visible, seek behaves
    correctly.
  - Tapping empty video area: controls visibility toggles as expected.
  - Tapping bottom bar padding (non-control area): no longer leaks through
    to toggle visibility.
- `./gradlew assembleDebug` — BUILD SUCCESSFUL.
